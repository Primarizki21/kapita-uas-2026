## 1. Framework mapping: SocioMathLLM → coding problems + collaborative debugging

Every claim in the left column is from [S1], §III–IV (`knowledge/SOCIOM~1.md:189-386`). The middle and right columns are **[INFERENCE]** unless a literature reference is given.

| SocioMathLLM component (as implemented in [S1]) | Direct coding analogue | What would have to be invented | What is lost |
|---|---|---|---|
| **Multimodal contextualization**: authentic context (2-D shapes, lengths/widths, annotated diagrams and real-life photos of tiles, windows, playgrounds) embedded in zero-shot prompts that produce **five candidate** MWPs (`SOCIOM~1.md:201-247`). | Authentic context = a real buggy program, its failing test output/traceback, and screenshots or IDE/UI artifacts; zero-shot prompts produce **five candidate debugging tasks** (buggy snippet + reproduction + test signal + question). | A definition of "authentic bug" (origin, reproducibility, environment/version pinning, licence), a multimodal schema for code artifacts, and a way to guarantee the seeded fault is real and the tests are discriminating. Literature support for treating debugging as an authentic practice: [1], [3]. | Elementary-geometry grounding in students' daily physical environment; the paper's specific claim that image-derived measurement properties make abstract geometry tangible [S1]. Screenshot-of-a-bug is a different kind of multimodality from photo-of-a-tile. |
| **Persona personalization via group profiles**: two-student group persona with group size, gender, socio-economic status, cognitive level, reading comprehension, mathematics response time, demographics and learning progress [S1] (`SOCIOM~1.md:248-254`). | Pair profiles with prior programming experience, language familiarity, prior debugging/task performance, driver–navigator preference, and pair composition. | Pedagogically defensible proxies for coding skill; instrumentation for "time-to-fix"; consent/privacy handling for student code logs. Pair-composition effects are a real variable in CS education [4], [10]. | The original profile is *mathematics*-specific (reading level, math response time, math progress); substituting technical proxies changes the construct being personalized, so the original personalization claim cannot be carried over unchanged. |
| **Four socialization competencies**: collaboration, cooperation, negotiation, ideas-sharing, each with an explicit definition and criteria; the MWP is redesigned to elicit that interaction [S1] (`SOCIOM~1.md:268-284`). | Collaborative debugging behaviours: joint fault localization (collaboration), driver/navigator and test-writing roles (cooperation), disagreement about root cause or patch (negotiation), explaining hypotheses and justifying a fix (ideas-sharing). | New operational definitions and rubric items for each competency *in debugging discourse*; evidence that a generated prompt actually elicits those behaviours. In [S1] the competencies were derived from math-socialization literature and expert review — they were **not** validated with students. | Subject-specific mathematical argumentation (justifying geometric reasoning) and the theoretical lineage the four competencies were borrowed from [S1]. Negotiation and ideas-sharing partially collapse into the same "explain your patch" talk in debugging [INFERENCE]. Evidence base: pair programming social dynamics [4], collaborative debugging [1], [3], peer review [11]–[15]. |
| **Few-shot instructional cues**: exemplars of hints for exchanging ideas, dividing tasks, justifying reasoning and co-constructing solutions [S1] (`SOCIOM~1.md:285-299`). | Debug-dialogue exemplars: "state a hypothesis before running", "ask your partner to reproduce the failure", "swap driver/navigator", "justify the patch against the failing test". | Expert-validated dialogue exemplars; checks that hints do not leak the fix or reduce the task to a script; mapping each cue back to one of the four competencies. | Math-specific co-construction of a shared solution and the authentic everyday-life phrasing of the original hints; the illustrative examples would all have to be rewritten [INFERENCE]. |
| **Three-module prompt pipeline**: (1) zero-shot five candidates from multimodal context → (2) CoT review against answerability, structure/clarity, multiple solution strategies and profile fit, selecting one → (3) socialization-focused refinement with few-shot cues; GPT-4o API, temperature = 1, no fine-tuning, three iterations per prompt [S1] (`SOCIOM~1.md:200-207, 248-295, 319-327`). | Structurally preserved: five candidate debugging tasks → CoT selection against compilability, reproducible failure, difficulty and pair-profile fit → refinement into a collaborative-debugging prompt, same no-fine-tuning/zero-shot/three-iteration protocol. | An **executable validation step** inside the loop (compile + run hidden tests in a sandbox), a machine-readable candidate representation (code + tests + context), and candidate-selection criteria for correctness/safety that [S1] never needed. | Prompt-only reproducibility: [S1] needs only an API key and prompt text, whereas code generation needs a pinned runtime, dependency set, test harness and sandbox [INFERENCE]. "Zero-shot from context alone" also becomes less clean when a reference implementation is needed to verify the bug. |
| **Automatic metrics + rubric/triangulation**: BLEU, METEOR, ROUGE-L, BLEURT and BERT precision/recall/F1 against reference MWPs; five mathematics teachers (>5 years' experience), orientation + calibration + consensus, 5-point rubric from the developed criteria, ICC; an LLM-as-judge scoring the same criteria [S1] (`SOCIOM~1.md:338-386`). | Execution-based checks (compile rate, fail-to-pass, pass@k, test-suite pass rate) plus an instructor rubric with ICC and an LLM judge; code-similarity metrics only as secondary diagnostics [27]–[30]. | A test harness and ground-truth patch per item; contamination and solution-leakage checks; a new CS-instructor panel and expert-validated rubric; sandboxing of generated code. | Numerical comparability with [S1]'s reported BLEU/ROUGE/BERT results, and reuse of the mathematics-teacher panel and math-geometry rubric. The original paper itself notes that BLEU underestimates quality when surface forms vary (`SOCIOM~1.md:425-433`), a problem that is *worse* for code, where many different patches are correct [27], [29]. |

**Summary verdict on the mapping [INFERENCE]:** five of the six components have a plausible structural analogue, but only the three-module pipeline and the "five candidates → CoT selection → refinement" skeleton transfer *as-is*. The artifact itself (MWP → code), the authenticity construct, the profile construct, the four competencies' theoretical grounding and the entire evaluation stack must be re-specified. That is a substantial re-theorization, not a relabelling.

## 2. Fit with the course brief

### What the brief actually says (translated from [B])

- Lines 18–19 list Topic 1 verbatim: *"SocioMathLLM: A Multimodal Large Language Model Framework for Generating Authentic Mathematical Word Problems Driving Socialization"* [B].
- Lines 17–24 enumerate four numbered topics, but line 25 says *"Carilah topik dan data yang serupa pada ketiga topik tersebut"* — "find topics and data that are similar **to/among the listed topics**" [B]. (The text says "the three topics" although four rows are printed; that inconsistency is in the brief itself [B].)
- Line 26 requires an English-language paper using the supplied template; lines 30–32 say *"Analisis tidak harus sama dengan topik yang ditentukan, tapi serupa"* — "the analysis need not be identical to the assigned topic, but must be **similar**" — and cap overlap between groups with the same topic at 20% [B].

### Verdict in plain language

**Conditional yes — but only if the generated artifact remains a mathematical word problem and collaborative debugging is used as an *instantiation of socialization*, not as a replacement for the problem type.** The word *serupa* ("similar") in [B] creates real room to change the analysis, the prompt strategy and the evaluation emphasis: the framework (multimodal LLM generation), the pedagogical goal (driving socialization) and the three-module engineering design can all survive a debugging-flavoured instantiation [INFERENCE]. Peer-reviewed CS-education work also makes collaborative debugging a legitimate social learning setting [1], [3], [4], [11]–[15].

**The risk, stated plainly: a pivot to "LLM-generated coding problems with collaborative debugging" as the *artifact* would very likely be judged a different topic, not a similar one.** Topic 1's central noun phrase is *authentic mathematical word problems* [B]; replacing it with code changes the artifact, the public dataset, the rubric, the raters' expertise and the automatic metrics simultaneously (Section 1). The brief's tolerance is for analyses that are *similar to the listed topics* [B], not for substitution of the defining construct. There is also no evidence in [B] that a cross-domain substitution is permissible, and the 20% overlap rule in [B] governs same-topic groups, not topic identity [INFERENCE].

**Smallest change that keeps the work inside Topic 1:** change **only the wording of the socialization prompt**, keeping everything else fixed — the authentic multimodal mathematical context, five zero-shot candidates, CoT selection on the original mathematics criteria, the four competencies, few-shot cues, GPT-4o/no-fine-tuning protocol, the rubric+ICC+LLM-judge evaluation, and the already-decided MathVista testmini ChartQA+TabMWP fallback item set (group decision recorded in the assignment context, not an external publication). Concretely, generate an authentic MWP that includes a *flawed worked solution from a partner*, and cue the pair to collaboratively locate and justify correcting the error. This still produces a mathematical word problem; collaborative debugging becomes the interaction mechanism for "collaboration", "negotiation" and "ideas-sharing" [INFERENCE]. A safe title would be *"…Generating Authentic Mathematical Word Problems Driving Collaborative Debugging as Socialization"*.

**If the team insists on generating code**, the honest framing is a *new* topic (LLM-based generation of programming problems for collaborative debugging), which is not what [B] asks for; it should not be presented as Topic 1 [INFERENCE].

## 4. Metric recommendation

**Baseline fact.** [S1] reports BLEU rising 0.002 → 0.408, ROUGE-L 0.124 → 0.570, METEOR 0.665 for SocioMathLLM, and BERT precision 0.859 → 0.906, recall 0.778 → 0.943, F1 0.817 → 0.925, alongside a five-teacher 5-point rubric and ICC (`knowledge/SOCIOM~1.md:393-406, 425-440`). The paper explicitly warns that BLEU underestimates quality when surface forms vary and that semantic equivalence matters more than literal matching in open-ended generation (`SOCIOM~1.md:416-433`).

**Do BLEU / BERT-style metrics transfer? [INFERENCE]**

- **Natural-language problem statement:** partly. BLEU/METEOR/ROUGE-L/BLEURT/BERT P/R/F1 remain computable against reference statements and are useful as *secondary*, reproducibility-friendly indicators of style and content coverage, exactly as [S1] used them. Their known weakness — penalizing valid paraphrases — is acknowledged by [S1] and documented in the metric literature [27], [28]. They must not be presented as measures of pedagogical or technical correctness.
- **Generated code:** mostly no. Many syntactically different patches satisfy the same tests, so n-gram overlap with one reference solution is actively misleading [27], [29]; embedding similarity to a reference string is not a correctness signal [30]. Code-aware similarity (CrystalBLEU [29], CodeBLEU-style AST matching) can be reported only as a diagnostic alongside execution results, never as the primary outcome.

**Defensible automatic metric set for a coding-problem analogue [INFERENCE]:**

1. **Primary — execution-based:** compile/parse success rate; **fail-to-pass rate** on the seeded bug; hidden-test pass rate; **pass@k** (at least k = 1, 5) for generated fixes; and, for *generated problems*, a **task-validity rate** = proportion whose stated bug reproduces and whose tests discriminate buggy from reference code. This follows the execution-grounded debugging evaluation precedent [21], [22], [23].
2. **Secondary — text similarity, clearly labelled:** BLEU/METEOR/ROUGE-L/BLEURT/BERT P/R/F1 on the *statement text only*, plus CrystalBLEU [29] on code if a reference solution exists. Report all of them with the caveat from [27], [28], [30].
3. **Human + LLM triangulation, mirroring [S1]:** an expert-developed rubric scored by CS instructors on a 5-point scale, with rater orientation, calibration and consensus, ICC for interrater agreement, and an LLM judge prompted with the same criteria; additionally score the four socialization competencies from the generated prompts (collaboration, cooperation, negotiation, ideas-sharing) using cues validated against [1], [3], [4], [11]–[15]. Report per-dimension means and ICC, not only an aggregate.
4. **Do not claim** that BLEU/BERT numbers are comparable to [S1]'s — the artifact, reference set and rating panel would all have changed [INFERENCE].
